# External AI review — two models, two briefs, and what changed

This file records a review that was run **before** this revision was published,
by two independent passes over the packet, and what this package did with each
finding. It is here because a package that says "reviewed externally" should let
a reader see the review rather than the claim.

- Channel: SiliconFlow (`https://api.siliconflow.cn/v1/chat/completions`), model
  `deepseek-ai/DeepSeek-V3`, temperature 0.3.
- Material given to both passes: `review-packet.md` and `AER1-CROSSWALK.md`,
  unedited, at the revision this file sits in.
- The reviewer was given no statement of what the authors believe and no list of
  expected findings.
- C3 was briefed as an independent **verification reader**; C4 as a **hostile
  rejecter** whose job is to find the fastest legitimate reason to reject the
  package. Both prompts are reproduced verbatim below, so the exercise can be
  repeated and disagreed with.
- Two limits worth stating: this is one model, twice, not two organisations; and
  an AI reviewer that has not run the code can only judge what the text supports.

### Two errors in the review itself

The C3 pass asserted that "D10 is record-unresolved plus check-incomplete" and
that "D16 is fail despite a revocation hold". Both are wrong against the
package: D10 carries one record-side code (`SOURCE_UNREACHABLE`), and D16's
revocation check is a **fail** (`REVOKED`), not a hold. They are left in the
verbatim reply below rather than tidied, because they show the limit of a
text-only review: a reader who cannot run the checker can misread a row, and a
human reviewer still has to check the check.

## The briefs, verbatim

**C3 system message:** an independent reviewer retained to assess a public
test-vector package submitted to an internet standards body, asked to be specific,
quote the text judged, and answer in English.

**C3 questions:** classify every claim as checkable-from-the-text / needs-code /
unsupported; whether the record-versus-checker boundary is precise enough for a
third party to classify a new case; whether the precedence rule is stated in one
place and matches the 18 rows; whether `absent` is the only crosswalk asymmetry;
and three findings ordered by discovery cost.

**C4 system message:** the hostile reviewer at the table, whose job is to find the
fastest legitimate reason to reject the package, then the second and third.

**C4 questions:** the strongest objection in a paragraph a chair would accept;
where the packet overclaims, split into stronger-than-evidence, true-but-misread,
and fine; what would have to be true for the cross-check to pass while both
implementations are wrong the same way; whether the AER-1 crosswalk is a genuine
interoperability datum or post-hoc alignment, and what in the document shows
which; and which number a competing implementation would attack first.

---

1. **Strongest objection**: The packet claims "all 102 vectors match the outcomes they state" but provides no evidence that these expectations were independently derived rather than generated by the reference implementation. The selftest only confirms that the checker reproduces its own outputs, not that the vectors encode correct behavior. This is circular validation.  

   **Second objection**: The policy boundary for D08 ("opaque content") is ambiguous. The packet states it is a policy choice but does not document alternative policies or how they would affect results, leaving the "hold" verdict unsupported for cases where real deployments might refuse.  

   **Third objection**: The AER-1 crosswalk misrepresents alignment by ignoring the critical `absent` state. The packet admits this asymmetry but dismisses it as a "policy choice," despite AER-1 explicitly treating absence as distinct from evaluation failure—a foundational distinction for revocation and delegation.  

2. **Overclaims**:  
   (a) "Two implementations agree" (crosscheck.py) implies robustness, but both implementations could share the same logic error. The packet does not prove independence (e.g., shared authorship or differential testing).  
   (b) "No cryptographic verification" is true but easily misread; the `signature: "ok"` stand-in risks being interpreted as a real check by skimmers.  
   (c) "Passing 120 rows is a floor" is fine—it correctly frames the set as a minimal test suite.  

3. **Two-implementation flaw**: The cross-check would pass if both implementations:  
   - Shared the same incorrect check order (e.g., testing revocation before subject binding).  
   - Misclassified `OPAQUE_CONTENT` as `check-incomplete` when it should be `fail`.  
   The packet does nothing to rule this out. The implementations could be forks or share a common library.  

4. **AER-1 crosswalk weakness**: The crosswalk is self-serving. It was generated *after* AER-1's publication (the script fetches AER-1's vectors) and selectively maps only compatible outcomes. The admission that `absent` is missing—a critical AER-1 case—reveals post-hoc alignment, not interoperability.  

5. **Target for competitors**: Attack the **56/120 fails**. A competitor would argue this skews toward negative testing, making the set useless for validating correct delegations. The distribution ("deliberate asymmetry") is arbitrary and undermines the set’s utility as a conformance floor. Quote: "Nine fails, eight holds ... The asymmetry is deliberate." This biases the suite toward catching errors rather than proving correctness.

## What this review does not establish

It does not establish that the claims are true. A model reading a packet can
agree with a false sentence as easily as with a true one, and neither pass ran a
single command. What it establishes is narrower and still useful: that two
readers briefed in opposite directions, given only the material, did not find the
packet self-contradictory, and that the objections they did raise were specific
enough to act on. The dispositions above say which ones were acted on and which
were not, and why.
