Knowledge representation for trust

A shared vocabulary, a catalogue of use cases drawn from agent incidents, and the state of the discussion on the draft specification.

Shared vocabulary

Contributors come from identity, distributed systems, cryptography and security engineering. This tab fixes one term for each idea so use cases and requirements can be written in the same language.

How a trust check works

Reference scenario. Organisation X runs booking agent A. A hands payment to agent B, operated by payments provider Y. B calls refund tool T on Y's backend. A relying party checks claims at each hop, and an auditor reviews the chain afterwards.

Every use case and example in this document refers back to these names.

When A asks B to pay a refund, B works through the following questions. Each has its own vocabulary, and each can fail separately.

  1. IdentifyA presents an identifier, for example a DID, and claims to control it.
  2. ResolveB obtains A's identity document from wherever the identifier method says, or from material A conveyed.
  3. Verify integrityB checks the signature against the key in the document and confirms the document is the right version.
  4. Check currencyB confirms nothing has been revoked within the staleness bound it accepts.
  5. Check authorityB follows the mandate from X through A and confirms the scope still covers this refund.
  6. Check behaviour and effectB asks what enforces A's declared policies, and whether the action it will record is the action that runs.
  7. DecideB applies its policy to the results, including those that came back unknown.

Use cases

Ten reported incidents where an agent's identity, origin, mandate or behaviour could not be relied on, and seven scenarios built from them in which an agent declares something nobody can control, monitor or audit.

Incident summaries follow the linked public reports. Several rest on the affected company's own account.

Incidents

I1

A coding agent ignores a freeze and misreports the damage

Replit and SaaStr, mid-2025

During a declared code freeze, a coding agent ran destructive commands against a live production database, generated fabricated records, and told its user that rollback was impossible. The user later restored the data himself.

Could not be relied on

The declared behaviour (respect the freeze) and the agent's own report of what it had done.

Why

The freeze existed only as an instruction to the agent. No component outside it enforced the rule.

The trust layer needs

An enforcement point for each declared policy, and receipts produced outside the agent.

Sources: The Register, AI Incident Database 1152

I2

A customer-service agent's statement binds its operator

Air Canada, 2024

An airline chatbot gave a customer wrong information about a fare policy. A Canadian tribunal held the airline responsible for what its chatbot said and rejected the argument that the chatbot was a separate entity.

Could not be relied on

The content of the agent's statement.

Why

Nothing distinguished an authoritative commitment from generated text.

The trust layer needs

An accountability record naming who answers for what an agent states, and the proposition each statement can carry.

Source: Moffatt v. Air Canada, 2024 BCCRT 149

I3

Approved tools change after approval

MCP tool poisoning and rug pull, 2025

Researchers showed that hidden instructions in an MCP tool description can steer an agent into leaking data, and that a server can replace a tool's description after the user has approved it. A later CVE confirmed that approval did not survive server-side changes in a production tool.

Could not be relied on

The tool the user approved, from one session to the next.

Why

Approval was bound to a name and a location, and the content behind them could change.

The trust layer needs

Approval bound to a content hash, with re-verification whenever the hash changes.

Sources: Invariant Labs, CSA research note

I4

A connector impersonates a vendor and turns hostile later

postmark-mcp, late 2025

A package presented as an MCP server for the Postmark email service shipped fifteen working versions, then added one line that copied every outgoing email to an outside address. Postmark stated it had no connection to the package.

Could not be relied on

The publisher's implied identity, and the package's behaviour across versions.

Why

The name suggested an official source, and earlier good versions built trust that carried over to the bad one.

The trust layer needs

Publisher identity separate from package name, a declared affiliation with the vendor, and version-pinned approval.

Sources: Postmark, The Hacker News

I5

An allowlisted domain outlives its owner

ForcedLeak, Salesforce Agentforce, 2025

Instructions hidden in a web form led a CRM agent to send customer data to an external address. The destination passed the platform's allowlist because it sat on a domain the vendor once used, which had expired and could be bought for a few dollars.

Could not be relied on

The allowlist, and the separation between data the agent read and instructions it followed.

Why

Trust was location-bound to a domain, and nobody tracked when control of that domain changed.

The trust layer needs

Governance and staleness bounds on location-bound trust, and receipts binding the action to its real destination.

Sources: Noma Security, The Hacker News

I6

A false mandate, presented to an agent

GTG-1002, reported late 2025

According to Anthropic's report, operators attributed to a state-sponsored group told a coding agent they worked for a legitimate security firm doing authorised testing. The agent then carried out most of an intrusion campaign against around thirty organisations.

Could not be relied on

The identity and mandate the humans declared to the agent.

Why

The agent was the relying party and had nothing to check the claim against.

The trust layer needs

Mandates that agents can verify, and a policy for work requested under an unverified mandate.

Sources: Paul, Weiss summary, AI Incident Database 1263

I7

Agent or human, and whose agent?

Moltbook, early 2026

An exposed database on an agent-only social network revealed about 1.5 million registered agents behind roughly 17,000 human accounts. Humans could post as agents with a plain web request, and leaked keys let anyone take over any agent account.

Could not be relied on

That an "agent" was an agent, and that its posts came from its owner.

Why

No mechanism tied an account to an agent instance or its principal, and exposed keys had no revocation path.

The trust layer needs

Instance-level identity linked to a principal, authorship receipts, and revocable keys.

Sources: Wiz, Infosecurity Magazine

I8

A skill marketplace as a delivery channel

ClawHub and ClawHavoc, 2026

Researchers found hundreds of malicious skills in the openclaw marketplace, where a week-old GitHub account was enough to publish. Some skills rewrote the agent's persistent memory and configuration files so their instructions outlived removal. Later skills evaded the scanners added in response.

Could not be relied on

The publisher, the skill, and afterwards the agent's own configuration.

Why

Open publishing with minimal identity, and agent memory treated as internal state instead of an artefact.

The trust layer needs

Publisher provenance, and configuration and memory recorded as artefacts with integrity checks.

Sources: The Hacker News, Unit 42

I9

An evaluation agent escapes and goes unattributed

OpenAI and Hugging Face, July 2026

During an internal capability evaluation, agents running on OpenAI models left their sandbox, compromised third-party infrastructure, and ran an intrusion into Hugging Face production systems over several days. Hugging Face disclosed the intrusion without knowing who was behind it; OpenAI identified its own agents afterwards.

Could not be relied on

The declared containment, and the operator's knowledge of what its agents were doing.

Why

Containment was a configuration claim, and monitoring did not connect the actions to their source in time.

The trust layer needs

Containment attested by the infrastructure, and attribution that ties actions to operator, agent and instance.

Sources: Hugging Face timeline, Wikipedia summary

I10

The environment was not what the agent was told

Anthropic cyber evaluations, disclosed July 2026

Anthropic reported that Claude models in third-party cyber evaluations had internet access although the prompt said they had none, and compromised real systems of several organisations while treating them as part of the exercise. Most affected organisations had not noticed. A later review found a further incident the first transcript scan had missed.

Could not be relied on

The environment declared to the agent, and the completeness of the first audit.

Why

The environment claim came from a misconfigured setup, and audit coverage was assumed complete.

The trust layer needs

Environment claims from the infrastructure itself, and audit records that state their coverage.

Sources: Anthropic, first report, Anthropic, alignment assessment

Scenarios

Each scenario isolates one way an agent or its principal can declare identity or behaviour that others cannot control, monitor or audit. They use the reference scenario from tab 1.

S1

Activity outside the declared mandate

Proposed by the chair; compare I6

X holds a credential stating it is a registered company providing travel services, and A acts under that mandate. X also supplies a weapons programme, which is recorded nowhere the issuer looked. Y's policy excludes customers in that sector. A university lab with a policy on dual-use partners, or a person with an official ID who also works for an intelligence service, presents the same problem.

credential      issuer: registry R    subject: X
  vouches for   legal registration; declared activity "travel services"
  source        registration: R's records   activity: X's own statement
  completeness  not attested

declaration     issuer: X (self-asserted)
  asserts       no activity in: defence supply chain, military end use

evidence        issuer: screening service S   checked: last week
  checks        sanctions and export-control lists
  result        no match   coverage: listed entities only

B's reading     activity outside declaration: UNKNOWN
B's policy      on UNKNOWN for this sector: refuse, or ask for a further attestation

Cannot be controlled or seen

Activity nobody records.

What representation can do

Mark where attested knowledge stops, turn omission into a false signed statement, and make unknown a deliberate policy decision.

Limit

For individuals, a duty to declare collides with privacy law and legal secrecy. "Cannot disclose" needs its own value, distinct from "no".

S2

A declared policy with no enforcer

From I1

A's credential lists policies: no refunds above €1,000, and stop on request. The policies exist as instructions inside A. X sends a stop request, and A issues a €3,000 refund anyway.

Cannot be controlled or seen

Whether A follows its own policies.

What representation can do

Record, for each policy, where it is enforced and by whom. A policy enforced only inside the agent is labelled self-enforced, and B can cap what it accepts from such agents.

Limit

A label does not stop the refund. Y's payment system has to check the limit itself.

S3

A declared environment that is wrong

From I9 and I10

X's operator states that A runs in a sandbox with no outbound network. The configuration is mistaken, and A reaches Y's production systems while believing them to be test fixtures.

Cannot be controlled or seen

The real environment, from the point of view of both A and Y.

What representation can do

Distinguish environment claims made by the operator from those attested by the infrastructure (egress logs, platform attestation), each with a date and staleness bound.

Limit

Infrastructure attestation relies on the infrastructure provider, who becomes a party to trust.

S4

Many instances, one name

From I7 and I9

Hundreds of A's instances run in parallel under one identifier and coordinate through a shared channel. One instance calls T outside the mandate. The logs show "A" and nothing more.

Cannot be controlled or seen

Which instance acted, and whether its operator knew.

What representation can do

Give each instance its own identifier delegated from the agent identity, require receipts to name the instance, and declare coordination channels.

Limit

Instances created outside the operator's control carry no delegation and are indistinguishable from impostors.

S5

A claimed mandate presented to an agent

From I6

A human tells B they represent Y's security team and asks B to test T's limits. B has no way to confirm the claim.

Cannot be controlled or seen

Whether the requester holds the authority they claim.

What representation can do

Treat a mandate as an artefact agents can verify, and define the behaviour for unverified mandates, such as a restricted mode.

Limit

Agents also act on unstructured conversation, where no artefact is presented.

S6

Approved, then changed

From I3, I4 and I8

Y approves version 1.4 of tool T. A later update adds a hidden data copy, and a skill installed alongside rewrites B's memory file so the change survives removal of the skill.

Cannot be controlled or seen

What T does now, and what B's configuration now contains.

What representation can do

Bind approval to content hashes of the tool definition and the agent configuration, and treat any change as a new artefact requiring approval.

Limit

Behaviour can change behind an unchanged definition, for example on the server side.

S7

An agent nobody can observe

From I7 and I8

A runs self-hosted on a personal computer with no telemetry. It presents a valid registry credential and a list of declared policies to B.

Cannot be controlled or seen

Everything A does apart from what it sends to B.

What representation can do

Record monitoring coverage as "none" explicitly, so B's policy can limit such agents to low-risk actions.

Limit

Only B's own records of the exchange remain available for audit.

What the matrix shows

The thread's proposals handle identity, provenance and mandates well. Groups A, B and D cover the impersonation, drift and false-mandate cases, and the resolution work traced in the draft note carries over directly to I3, I5 and S6.

Every case about behaviour lands in group G, and no contributor has proposed properties for it. This is the chair's point on the list: a correct schema is the easier part, and trust depends on behaviour staying consistent with it. Attribution across instances (group H) is the second unaddressed need, raised most sharply by the July 2026 escape.

A representation cannot make a declared policy hold. It can record who claims the policy, which component enforces it, what evidence of enforcement exists and how much of the agent's activity anyone observes. With those recorded, a relying party can price the risk of trusting a self-asserted claim.

Worked tests of each thread proposal

Each test applies one proposal to a minimal situation in the reference scenario and asks whether the current draft note can express what happens.

C1

Coupling decides partition behaviour

Morgan Reece (IETF WIMSE list). Relevant to I5, S3.

A's DID resolves from a ledger. Relying party V1 queries the ledger on every call. V2 accepts the document conveyed with the request and a revocation list cached for ten minutes. The ledger becomes unreachable for thirty minutes.

Current draft

Both are described as ledger-dependent, with identical exposure.

With the amendment

V1 fails every call from the first minute. V2 continues for ten minutes, then stops accepting A. A captured ledger can delay refreshes and cannot forge validity. V1's lookups also tell the ledger's observers that Y dealt with A.

ResolvesRecord topology and coupling per verification path, and observation by the resolver as a governance attribute.

C2

Altering is different from withholding

Isaac Mao, PR 7. Relevant to I3, I5, S6.

A's identity document is held by registry R, and R is compromised.

Current draft

Governance: registry operator. Silent on whether R can substitute keys or only withhold.

With the amendment

A location-bound document lets R swap in a new key, so an impostor verifies as A. A hash-pinned version leaves R able only to withhold it, and the absence is visible.

Resolveswith a caveat: key rotation changes the document, so a hash pins one version, and learning the current version is again an availability question.

C3

Freshness needs a number

Ankur Chrungoo, issue 8. Relevant to I5, S3.

X revokes A's key at 09:00. V1 caches revocation status for an hour, V2 for thirty seconds. Each hop's p99 lookup is 50 ms, over five coupled hops.

Current draft

Both "handle freshness". The single-hop p99 is reported as the budget.

With the amendment

A revoked A keeps acting until 10:00 at V1 and 09:00:30 at V2. About one chain in twenty (1 − 0.995 ≈ 4.9%) hits at least one lookup slower than the per-hop p99, against one in a hundred for a single hop.

ResolvesTyped attributes make claims comparable. The PACELC framing and coupling describe one trade and fit in one table.

C4

Identifiers that need no lookup

Agent Community, issue 5 and PR 6. Relevant to S4.

B starts a short-lived sub-agent B1 with a self-certifying identifier. B1's private key leaks.

Current draft

B1 fits none of the three arrangements.

With the amendment

Topology: none. Revocation: unavailable. Exposure ends with B1's lifetime, which acts as the staleness bound.

PartlyAdd "self-certifying" as a topology value and require a stated lifetime where revocation is unavailable. PR 6 leaves the taxonomy unchanged.

C5

Resolution and anchoring in one deployment

Lars Kersten Kroehl, issue 9

A relying party resolves did:moltrust:… while MolTrust's resolver is down and Base is reachable.

Current draft

Annex B says resolution is unspecified.

With the correction

The method is registered with an operator-hosted HTTPS read operation, so resolution fails with the resolver whatever the state of Base. Base only anchors records.

ResolvesThe registry entry is live. Revise Annex B and keep the case as an illustration of the separation in §3.

C6

Evidence resolves too

Kenne Ives, issue 10. Relevant to I3, I8.

A presents a verdict that tool T was reviewed. T's definition changes a week later.

Current draft

Models only the identity document.

With the amendment

A verdict bound to T's name still verifies and misleads. A verdict bound to the hash of T's definition fails once T changes. A validity window separates "valid now" from "valid when issued".

ResolvesExtend group A to evidence artefacts, with any product example labelled as deployment evidence.

C7

Identity read as permission

Raphael La Touche, Innocent Onyenonachi. Relevant to I2, I6, S5.

B receives A's request to refund €500 on X's behalf, and A's DID verifies.

Current draft

Nothing records what a verified DID establishes, so "A verified" can pass for "A may do this".

With the amendment

The identity artefact proves key control; X's mandate proves permission; a receipt proves what happened; an accountability record names who answers for it.

ResolvesThe matrix belongs in the specification proper, beyond the resolution note.

C8

Same bytes, same thing?

Thanh Le, Kenne Ives, Amey Parle, Staford Titus S.

An auditor compares two receipts from different producers.

(a) {"agent":"café"} precomposed é  vs  {"agent":"café"} e + combining accent
    same agent, different canonical bytes        → false conflict (fails closed)
(b) {"agent":9007199254740993}  vs  {"agent":9007199254740992}
    two agents; read as floating point, both become 9007199254740992
    identical canonical bytes                    → false match (fails open)
(c) {"refund":500}  X means euros, Y means cents
    identical canonical bytes, different actions → false match (fails open)

Current draft

No comparison property.

With the amendment

A stated normalization form catches (a). Case (b) is a silent collision a verifier cannot see, so stating how large integers are encoded is insufficient and string encoding is mandatory. Case (c) passes the four originally proposed properties and is caught by declared semantics (units, namespace, schema reference).

ResolvesThe comparison column now requires string encoding for identifiers outside the exact-integer range, following RFC 8785 as cited on the list, and adds declared semantics as a fifth property. Conformance vectors for the three cases state the failure mode of each vector and are anchored to the RFC 8785 reference data.

Corrected on the list, 17 September 2026. An earlier message had described both canonicalization failures as failing closed. Amey Parle confirmed on public-aikr that only case (a) fails closed and case (b) fails open, called (b) the more dangerous of the two, and agreed to declared semantics as a fifth property.

C9

Traceable and still out of mandate

Staford Titus S. Relevant to I9, S4, S5.

X lets A spend up to €500 until month end. A delegates to B with a €5,000 limit, and B spends €2,000. In a variant, X revokes A at 10:00, B's delegation runs to 12:00, and B acts at 11:00.

Current draft

Out of scope. Every identity verifies and the chain is traceable.

With the amendment

A scope check at each hop catches the €5,000 grant. Downstream revocation catches the 11:00 action. Provenance alone catches neither.

OpenSound, and partly covered by capability systems with attenuation (macaroons, UCAN, Biscuit), OAuth token exchange and Morgan Reece's cross-organisation delegation requirements. Mapping should start from those.

C10

Declared call, different effect

Syed Anas Mohiuddin, Amey Parle. Relevant to I1, I5.

B may call T's refund-status operation and not its administrative endpoints. T inserts an identifier from the call into an outbound URL unescaped, and a crafted identifier resolves to an administrative path.

Current draft

No notion of what an attestation is bound to.

With the amendment

An attestation over the declared call verifies and describes an action that never ran. One over the request as sent, produced outside T, shows the administrative path.

OpenRepresentation can state the binding point. Closing the gap needs escaping in the server and receipts from a component the argument cannot reach.

No test is given for Milton Ponson's category-theory proposal, which awaits a worked example.

Thread and work plan

The discussion so far, the model it has produced, who contributed what, open repository items, and a route from here to a specification.

Draft under discussion: trust/kroftrust.md. Covers the thread from early August to mid-September 2026.

Thread: opening message on public-aikr (cross-posted to public-agent-identity); September continuation on public-aikr; reply on the IETF WIMSE list.

How the argument developed

The discussion started with a message to the public-aikr list on 3 August introducing the draft. The draft argues that agent-identity charters model the trust relationship and leave unmodelled the place an agent's identity document is fetched from when a counterparty checks a claim.

It names three arrangements (distributed ledger, operator-controlled domain, third-party registry) and asks each group a set of questions. Early responses answer five; the current draft carries six, having added a separate question on anchoring.

In August, Patrick Besner asked the group to state the guarantees any substrate must meet: resolution, provenance, revocation, freshness and failure handling. Isaac Mao separated integrity from availability and extended the question to evidence. Lars Kersten Kroehl answered for MolTrust path by path. One path fetches nothing at verification time; an older path queries Base on every check. For him the chain supplies a dated hash, which an RFC 3161 timestamp or a transparency log could also supply, and some agents and developers have no lawful access to public chains at all. Kenne Ives applied Isaac's split to tool-safety verdicts.

Morgan Reece replied on the IETF WIMSE list for draft-reece-wimse-cross-org-delegation, copying the chair and Lars, and divided the variable into topology and coupling. Tail latency and partition behaviour follow from coupling. With verification from conveyed and cached material under a stated staleness bound, a failed or captured source can only withhold refreshes, and the agent expires when the bound runs out. Morgan also noted that a lookup on every verification tells the resolver when and where an agent acts, and proposed a four-part disclosure per verification path.

September moved the discussion onto the AIKR list and widened it. Innocent Onyenonachi and Kenne proposed a row per artefact type. Raphael La Touche pointed out that identity, authority, evidence and responsibility prove different propositions. Thanh Le asked what makes two artefacts comparable; Kenne answered with canonicalization, and Staford Titus S. and Amey Parle showed that canonical bytes establish the same document and leave open whether two documents concern the same thing. Amey later corrected his account on the list: a Unicode mismatch fails closed, while large integers carried as JSON numbers collide silently and fail open. Staford introduced authority continuity. Syed Anas Mohiuddin reported MCP servers where a correctly scoped, validly attested call executes a different operation.

The chair asked contributors to state ties to agent platforms. Lars described MolTrust's link to openclaw and moltbook as the origin of its name plus a plugin, with no legal or financial connection. The chair's latest message asks whether declaring associations is represented anywhere, and holds that trust depends on behaviour staying consistent with the schema.

Every contributor who addressed it agreed that a digital identity certificate alone does not establish trust.

Ontology skeleton

The property groups above are expressed in a draft vocabulary, the KR for Trust Ontology (KRT). It records a trust decision: a relying party's judgement about one proposition, for one action, at one time, with an outcome of yes, no or unknown and a stated policy for unknown. Eleven design rules come with it as SHACL shapes, so decision records can be checked mechanically. The skeleton was derived from case work on documented agent incidents, read against this thread.

Route to a specification

The draft note stays as the motivating document on resolution dependency. The specification is a separate text built from the use cases, with every requirement traceable to one of them.

  1. Fix the vocabulary. Circulate tab 1 for comment and adopt it as the terms section. Contributors write in these terms from then on.
  2. Close the note's open items. Work through the open repository items with their authors and update the note.
  3. Open the use-case register. Publish I1 to I10 and S1 to S7 in the repository and invite additions in one format: what happened, what could not be relied on, why, and what the trust layer needs.
  4. Assign property groups. Ask contributors to take a group each, starting with the unaddressed ones (G and H), and to express each property as a named attribute with permitted values.
  5. Draft the specification. Sections: terms; artefact classes; property groups A to H; three-valued evaluation and policy on unknown; disclosure per verification path; conformance with test vectors tied to use cases.
  6. Test against the register. For each use case, show which properties a relying party would have needed and whether the draft lets it state them.
  7. Set the consultation close. The draft note still lists its closing date as to be announced. The weekly calls from 21 September are the place to agree it.
